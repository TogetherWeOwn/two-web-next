# Community human participation metrics

This page maps the current **The TWO Community** goal to the data interfaces available in this repository. It defines what each goal metric means operationally, distinguishes complete sources from partial proxies, and records where the current interfaces cannot produce a human-only value. It does not change goal policy or authorize monetization.

## Goal wording and reporting rule

The community goal defines:

- **Weekly active humans:** a human with at least one message **or** at least 10 voice minutes during the week; bot traffic does not count.
- **Human messages/week:** number of human messages in a week; bot traffic does not count.
- **Joins/week:** joins during a week; bot traffic does not count.
- **Event attendance:** attendance at community events. The goal sets no numeric attendance threshold. Separately, its event gate is one event held weekly for four consecutive weeks.

Use the goal's weekly reporting period and state its exact start/end timestamps and timezone with every reported value. The goal does not specify a timezone or week-boundary convention; this document does not select one. Until that convention and a source are agreed, label the period or value **ambiguous / unavailable** rather than silently choosing a boundary. Never turn missing, stale, inaccessible, or non-comparable source data into zero. Zero is valid only when a complete, current source explicitly reports zero for the stated interval.

## Source details and limits

- The bot-owned `web_v1.live_counts.human_member_count` is a nullable, guild-wide snapshot: “Human members, not bots”; null means unknown, not zero. It is not a time series or an activity count. See [the `web_v1` contract](web-v1-contract.md#web_v1live_counts).
- The join flow records terminal attempt outcomes, source, request ID, Discord ID, and timestamp. `/hotzones/joins` and its aggregate count both `added` and `already_member`, so they are not a new-join count; use raw `join_attempts` rows filtered to `outcome = 'added'` for the website-flow-only proxy. That still does not turn a web-flow sample into all guild joins. Join attempts are retained for 90 days. See [`recordAttempt`](../src/join/service.ts) and the [join aggregates](../src/hotzones/aggregates.ts).
- The event schema records event timing and RSVP answers. One RSVP row per member/event is maintained, but its status describes an answer, not verified presence. See the [event and RSVP schema](../src/db/admin-schema.ts).
- The privacy policy states that message content is never stored in the website database. This does not establish what a separate bot system may retain; no such bot message/voice source is part of the website interface reviewed for this definition. The hot-zone `voice` view includes a deterministic WhatPulse-seeded prior and is explicitly an estimate, not member-level voice minutes; do not use it to satisfy the ≥10-minute active-human criterion. See [privacy policy](../content/privacy-policy-v3.md) and [hot-zone aggregates](../src/hotzones/aggregates.ts).

## Recording missing or ambiguous data

For each weekly scorecard row, record the metric, exact period and timezone, source/interface, value, and one of `reported`, `partial proxy`, `unavailable`, or `ambiguous`. Include the coverage or exclusion limitation for a partial proxy. Leave the value blank for unavailable or ambiguous data and state why; do not write `0`, estimate, interpolate, or reuse a different metric as a substitute. A source change or a new human/bot rule requires updating this map before claiming comparable values.
