# Community human participation metrics

This page maps the current **The TWO Community** goal to the data interfaces available in this repository. It defines what each goal metric means operationally, distinguishes complete sources from `Partial` ones, and records where the current interfaces cannot produce a human-only value. It does not change goal policy or authorize monetization. Which sources may be used for a scorecard, and the access boundary around them, are governed by [community metrics: source and access boundary](community-metrics-access.md); the reporting format is the [weekly community scorecard](community-weekly-scorecard.md). This page is the source map those documents point to, and it uses their status labels.

## Goal wording and reporting rule

The community goal defines:

- **Weekly active humans:** a human with at least one message **or** at least 10 voice minutes during the week; bot traffic does not count.
- **Human messages/week:** number of human messages in a week; bot traffic does not count.
- **Joins/week:** joins during a week; bot traffic does not count.
- **Event attendance:** attendance at community events. The goal sets no numeric attendance threshold. Separately, its event gate is one event held weekly for four consecutive weeks.

Use the weekly reporting convention below and state its ISO week label and exact UTC start/end timestamps with every reported value. The convention settles period identity only: an unavailable source or unresolved population, bot classification, or measurement meaning still requires **Not reported — scope unclear** or **Not reported — source unavailable**. Never turn missing, stale, inaccessible, or non-comparable source data into zero. `0 (verified)` is valid only when a complete, current source covers the stated interval and explicitly reports zero for it.

## Weekly reporting convention

Adopted 2026-10-20: use ISO weeks in UTC, from Monday 00:00:00 inclusive to the next Monday 00:00:00 exclusive. State the ISO week-year and week number as `YYYY-Www` together with exact UTC `[start, end)` timestamps; for example, `2026-W10: [2026-03-02T00:00:00Z, 2026-03-09T00:00:00Z)`. This is a reporting convention only, not a change to goal targets or policy; it supplies no measured values and approves no new source.

UTC has no daylight-saving transitions, so every reporting week is 168 hours, including weeks with a 23- or 25-hour local day. Use the ISO week-year (week 1 contains the first Thursday), not the calendar year of an individual day. `2026-W53: [2026-12-28T00:00:00Z, 2027-01-04T00:00:00Z)` contains New Year's Day 2027; `2027-W01` starts at that exclusive end. W53 is a full week where present; W52 → W01 in a 52-week year and W53 → W01 in a 53-week year are adjacent, with no stub weeks.

Assign an event to the reporting week containing its start instant in UTC; keep the event's host-timezone display unchanged. Held-event evidence uses the observed actual start; a planned slot uses its scheduled start and does not establish that the event was held. Carry the note **“counted by UTC instant, displayed in host zone”** on scorecards. A Sunday 20:00 event in `America/Chicago` starts on Monday in UTC and belongs to the next reporting week. This can split local evening activity at a week edge. Activity metrics still use activity instants within their reporting interval, not an event's display date.

The [four-week readiness run](community-monetization-readiness.md#readiness-condition) and [eight-week growth review](community-growth-review.md#evidence-for-the-review) use this same calendar grid. Consecutive weeks have adjoining boundaries, including across ISO year changes; never hide or compress a missing calendar week. Each procedure retains its own evidence and decision rules. This aligns with `/hotzones` UTC half-open windows but adds no weekly window there: its smallest selectable window remains a calendar month, so the Joins/week source limitation below is unchanged.

## Source details and limits

- The bot-owned `web_v1.live_counts.human_member_count` is a nullable, guild-wide snapshot: “Human members, not bots”; null means unknown, not zero. It is not a time series or an activity count. See [the `web_v1` contract](web-v1-contract.md#web_v1live_counts).
- The join flow records terminal attempt outcomes, source, request ID, Discord ID, and timestamp. For scorecards, the only approved joins source is the `/hotzones` joins grid (`loadJoinsGrid`): it counts both `added` and `already_member` as recorded successful join-attempt outcomes and drops attempts linked to `leaderboard_opt_out = true` profiles, so it is not a new-join count but it does preserve the opt-out promise. The grid is reachable only through `?season=`, which accepts only absent/`all`, `YYYY`, `YYYY-MM`, or `YYYY-Qn` UTC windows ([season grammar](../src/hotzones/season.ts)); the smallest window is a calendar month, so the grid cannot produce a joins/week value and the weekly Joins cell is **Not reported — scope unclear**. Cite the grid only as separate context for its exact season window (month, quarter, year, or all-time), never as a weekly value. Unfiltered join counts — including the admin join funnel and any raw `join_attempts` count, even one selecting only `added` (or only `added` and `already_member`) — are not approved for scorecards; an `added`-only source requires CISO review and an opt-out filter first. Join attempts are retained for 90 days. See [source and access boundary](community-metrics-access.md), [`recordAttempt`](../src/join/service.ts), and the [join aggregates](../src/hotzones/aggregates.ts).
- The event schema records event timing and RSVP answers. One RSVP row per member/event is maintained, but its status describes an answer, not verified presence. See the [event and RSVP schema](../src/db/admin-schema.ts).
- The privacy policy states that message content is never stored in the website database. This does not establish what a separate bot system may retain; no such bot message/voice source is part of the website interface reviewed for this definition. The hot-zone `voice` view includes a deterministic WhatPulse-seeded prior and is explicitly an estimate, not member-level voice minutes; do not use it to satisfy the ≥10-minute active-human criterion. See [privacy policy](../content/privacy-policy-v6.md) and [hot-zone aggregates](../src/hotzones/aggregates.ts).

## Recording missing data

For each row of the [weekly community scorecard](community-weekly-scorecard.md), record the metric, exact period and timezone, source/interface, value, and one of the scorecard's completeness labels: `Complete`, `Partial`, or `No source data`. Include the coverage or exclusion limitation for a `Partial` value. Leave the value blank and write **Not reported — source unavailable** or **Not reported — scope unclear** when no approved source exists or its scope cannot be verified; do not write `0`, estimate, interpolate, or reuse a different metric as a substitute. Use `0 (verified)` only as defined in the scorecard. A source change or a new human/bot rule requires updating this map — and, where the [source and access boundary](community-metrics-access.md) requires it, CISO review — before claiming comparable values.
