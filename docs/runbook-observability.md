# Observability and incident triage

This runbook is the entry point for diagnosing a TWO Web Next incident. Use
Cloudflare Workers Observability for source logs and the existing `two-web-next-alerts`
Tail Worker for redacted Discord ops notifications. Staging is the first place to
exercise a probe. Production checks are passive: do not inject faults, submit a
probe, or change production state as part of diagnosis.

## From a notification to the cause

1. Open the Cloudflare dashboard and select **Workers & Pages → the Worker named
   in the alert → Observability → Logs**. Select the environment and time window
   from the alert. The alert's route/job and timestamp are safe summary fields.
   The source error class is logged internally, but neither the class nor an
   exception is sent to Discord.
2. Search the source stream for the incident's environment. Staging HTTP request
   failures come from `two-web-next`; staging terminal queue failures come from
   `two-web-jobs`. In production, both HTTP request and queue failures come from
   `two-web-next-production` (its production queue consumers run on the web
   Worker). The Tail stream (`two-web-next-alerts` in staging,
   `two-web-next-alerts-production` in production) records `ops.alert.delivered`
   and `ops.alert.delivery_failed` receipts. The source record may be absent for
   `uptime.down`, which is generated by the Tail Worker.
3. For an HTTP incident, use the member-visible `x-request-id` / Support
   reference when the response provides one to find the `http.request` record and
   then any `error.alert` or `queue.failing` record with the same `request_id`.
   Query serialized JSON log messages with a contains filter; do not assume
   `request_id` is indexed. MCP tool errors on `/mcp` are an exception: the SDK
   returns an `isError` result instead of throwing, and the alert call does not
   receive the request ID, so there is no same-ID error-alert record to correlate.
   See [request correlation in Workers Logs](runbook-logs.md#find-a-request).
4. For a queue incident, filter the environment's source Worker (`two-web-jobs`
   in staging, `two-web-next-production` in production) by the safe job class and
   inspect its terminal `queue.failing` source record. Request-produced jobs
   preserve their `request_id`; scheduled jobs and older queue messages may not
   have one. See [alert source lines](runbook-alerts.md#source-lines) and
   [sync retry diagnostics](runbook-alerts.md#sync-event-retry-cause-diagnostics).
5. Determine the deployed revision using the staging `/up` response when
   available, or the deployed version in Cloudflare. Staging `/up` exposes the
   Worker version tag and version ID. Production currently has no
   `CF_VERSION_METADATA` binding, so its `/up` response does not provide a
   revision marker. Do not infer a deployed SHA from the current `main` branch.
6. In Cloudflare, open the production Worker's deployed version and read its
   tag, which is `<40-hex-sha>-<GitHub-run-id>-<run-attempt>`. Use the first
   component as the deployed source SHA and the second as the production deploy
   workflow run ID; do not compare the full tag to the SHA. Open that exact run
   in [GitHub Actions → deploy-production](https://github.com/TogetherWeOwn/two-web-next/actions/workflows/deploy-production.yml),
   then confirm its resolved `DEPLOY_SHA` matches the tag's SHA. For staging,
   use the staging `/up` version tag and the corresponding
   [GitHub Actions → deploy-staging](https://github.com/TogetherWeOwn/two-web-next/actions/workflows/deploy.yml)
   run. The dispatch run's head can differ from the promoted commit; its head SHA
   is not deployment evidence. The production workflow creates the GitHub Release
   only after a successful promote. Open the deployed commit's PR list or inspect
   its commit message and changed files to identify the change that introduced
   the error. The
   [releases page](https://github.com/TogetherWeOwn/two-web-next/releases)
   provides release notes and links back to merged pull requests.
7. If the notification has no matching receipt, check the Tail Worker's own
   Observability logs for a redacted delivery failure. A missing or invalid
   `OPS_ALERT_WEBHOOK_URL` silently disables outbound delivery. Never print,
   copy, or paste the webhook value; the
   [alert runbook](runbook-alerts.md#configuredeploy-staging-first) describes
   safe configuration and the staging-only delivery drill.

## Alert coverage and limitations

- `error.alert` covers unexpected HTTP error paths and is muted per error-class
  and route fingerprint for five minutes per isolate. It is not an aggregate
  5xx/error-rate alarm.
- `queue.failing` covers terminal queue failures. Retryable failures do not page
  until terminal; inspect the retry-cause records for context.
- The scheduled Tail Worker probe checks `/up` every five minutes and alerts
  after two failed attempts in one run. It detects sustained unavailability,
  not a two-minute SLO window or the full sign-in/member journey.
- Discord notifications are allowlisted, redacted summaries. They do not contain
  a request ID, exception text, URL, or build SHA; correlate them with source
  logs and the deployed version in Cloudflare.
- Cloudflare Workers Observability is the configured error/logging surface; this
  repository does not configure a Sentry SDK. The production GitHub Release
  identifies the promoted commit, but request/error log lines are not currently
  tagged with that SHA. Staging `/up` exposes its deploy version metadata.
- Production rollout uses the shared 5/50/100 gradual promotion action with
  per-stage health/SLO gates and automatic rollback on a failed gate. This
  rollback is driven by the promotion gates, not a live aggregate error-rate
  monitor. See [production promotion and rollback](runbook.md).

These limitations are explicit: do not treat a healthy `/up`, an absent Discord
page, or a GitHub Release as proof that the full user journey is healthy or that
an error-rate threshold is being monitored. Expand detection only through a
reviewed change with staging evidence and passive production verification.

## Safe verification

Use the authenticated alert probe and require both fresh redacted Tail receipts
on staging, as described in
[the alert delivery drill](runbook-alerts.md#probe-parity-request-error--self-failing-queued-job).
The probe deliberately returns HTTP 500 and may emit one synthetic terminal queue
failure; it must not be run against production. For log correlation and redaction
tests, see [request-log tests](../test/request-log.test.ts) and
[alert redaction tests](../test/tail-alerts.test.ts).

Never put webhook URLs, tokens, cookies, OAuth callback parameters, member IDs,
raw traces, or raw Tail streams in an issue, PR, or shared incident note. Use
only the redacted probe result and the deployed 40-hex source SHA as evidence.
