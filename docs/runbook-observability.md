# Observability and incident triage

This runbook is the entry point for diagnosing a TWO Web Next incident. Use
Cloudflare Workers Observability for source logs and the existing `two-web-next-alerts`
Tail Worker for redacted Discord ops notifications. Staging is the first place to
exercise a probe. Production checks are passive: do not inject faults, submit a
probe, or change production state as part of diagnosis.

## From a notification to the cause

1. Identify the environment first from the delivering Tail Worker or the
   webhook channel that received the page (`two-web-next-alerts` is staging,
   `two-web-next-alerts-production` is production); when in doubt, check both
   Tail receipt streams. Trace-derived Discord summaries carry the exact
   source `script`, a fixed `logs` dashboard path, and `build_sha` when the
   trace's version tag or its release-tagged log lines carry one, alongside event, fingerprint, route/job,
   and timestamp. `uptime.down` and `synthetic.down` are generated by the Tail
   Worker itself and carry no `script` (status for `uptime.down`; check,
   target host, and status for `synthetic.down`), so use the delivering Tail
   Worker or channel for those events; both carry the paging run's optional
   `build_sha` (and `version_id`) from the `/up` revision marker for deploy
   correlation. Then open the Cloudflare dashboard at
   the summary's `logs` path (or the step-2 mapping for the Tail-generated
   events) for the alert's time window. The source error class is logged
   internally, but neither the class nor an exception is sent to Discord.
2. Search the source stream for the incident's environment. Staging HTTP request
   failures come from `two-web-next`; staging queue/scheduled failures come from
   `two-web-jobs`. Production HTTP request failures come from
   `two-web-next-production`. Production queue/scheduled failures come from the
   live consumer/cron owner: `two-web-jobs-production` after the corresponding
   transfer, or `two-web-next-production` while that transfer is pending.
   Require authorized read-only consumer and cron ownership evidence per
   [Queue incident targets by environment](runbook.md#queue-incident-targets-by-environment-checked-in-expectations-live-readback-required);
   `node ci/check-production-triggers.mjs` checks both against the reviewed
   topology. Do not infer completion from config or a version promotion. If
   ownership is partial or unreadable, inspect both production source streams
   and report/reconcile the gap; silence is not proof of health. The Tail stream
   (`two-web-next-alerts` in staging, `two-web-next-alerts-production` in production)
   records `ops.alert.delivered` and `ops.alert.delivery_failed` receipts. The
   source record may be absent for `uptime.down` and `synthetic.down`, which are
   generated by the Tail Worker.
3. For an HTTP incident, use the member-visible `x-request-id` / Support
   reference when the response provides one to find the `http.request` record and
   then any `error.alert` or `queue.failing` record with the same `request_id`.
   Query serialized JSON log messages with a contains filter; do not assume
   `request_id` is indexed. MCP tool errors on `/mcp` correlate the same way:
   the SDK returns an `isError` result instead of throwing, but the tool server
   is built per request with that POST's request ID, so its `error.alert`
   record carries the same `request_id` as the `http.request` record.
   See [request correlation in Workers Logs](runbook-logs.md#find-a-request).
4. For a queue incident, filter the environment's source Worker (`two-web-jobs`
   in staging; in production, the step-2 readback's consumer owner,
   `two-web-jobs-production` after transfer or `two-web-next-production` while
   pending) by the safe job class and inspect its terminal `queue.failing`
   source record. For a scheduled incident, use that readback's cron owner and
   `scheduled.failing`, not an assumed queue owner. Request-produced jobs
   preserve their `request_id`; scheduled jobs and older queue messages may not
   have one. See [alert source lines](runbook-alerts.md#source-lines) and
   [sync retry diagnostics](runbook-alerts.md#sync-event-retry-cause-diagnostics).
5. Determine the deployed revision from the affected Worker's deployed version,
   not from a different Worker's health response. Staging `/up` exposes only the
   web Worker's version tag and version ID; it says nothing about the separately
   deployed `two-web-jobs` Worker. For a staging queue incident, open the deployed
   `two-web-jobs` version in Cloudflare and use its tag. The staging web and jobs
   Workers are normally tagged with the same SHA by one deploy run, but can
   diverge after a partial deploy or an independent rollback, so check both tags
   when the incident spans both Workers or their versions may differ. Every
   structured source record also carries its emitting Worker's `build_sha` and
   `release`, so one Worker's line never borrows the other's build. Production
   declares `CF_VERSION_METADATA` too, so its `/up` carries the same revision
   marker staging does. Do not infer a deployed SHA from the current `main` branch.
6. In Cloudflare, open the production Worker's deployed version and read its
   tag, which is `<40-hex-sha>-<GitHub-run-id>-<run-attempt>`. Use the first
   component as the deployed source SHA and the second as the production deploy
   workflow run ID; do not compare the full tag to the SHA. Open that exact run
   in [GitHub Actions → deploy-production](https://github.com/TogetherWeOwn/two-web-next/actions/workflows/deploy-production.yml)
   and use the `deploy-production` job's resolved `DEPLOY_SHA`. The resolved SHA
   can differ from the workflow dispatch revision; confirm the tag's SHA prefix
   matches `DEPLOY_SHA`, not the dispatch revision. For staging,
   use the affected Worker's deployed tag, then find the matching
   [GitHub Actions → deploy.yml (`deploy-staging` job)](https://github.com/TogetherWeOwn/two-web-next/actions/workflows/deploy.yml)
   run by its title, `deploy <SHA>`. Confirm the `deploy-staging` job succeeded
   and the title SHA matches the Worker tag; a run title alone is not proof of a
   successful deploy. The production workflow creates the GitHub
   Release only after a successful promote. Open the deployed commit's PR list or
   inspect its commit message and changed files to identify the change that
   introduced the error. The
   [releases page](https://github.com/TogetherWeOwn/two-web-next/releases)
   provides release notes and links back to merged pull requests.
7. If the notification has no matching receipt, check the Tail Worker's own
   Observability logs for a redacted delivery failure. A missing or invalid
   `OPS_ALERT_WEBHOOK_URL` silently disables outbound delivery. Never print,
   copy, or paste the webhook value; the
   [alert runbook](runbook-alerts.md#configuredeploy-staging-first) describes
   safe configuration and the staging-only delivery drill.

## Alert coverage and limitations

- `error.alert` covers unexpected HTTP error paths and is muted per error-class
  and route fingerprint for five minutes per isolate. Each isolate tracks at most
  500 active fingerprints; while all slots are occupied, new fingerprints stay
  silent rather than evicting an active mute.
- `error.spike` is the aggregate alarm: the Tail Worker counts every trace
  outcome per script in a Durable Object and pages once (15-minute cooldown)
  when a rolling five-minute window holds at least 5 error responses that are
  at least half of requests, or at least 5 crash outcomes (`exception`,
  `exceededCpu`, `exceededMemory`, `scriptNotFound` — crash loops, including
  invocations that emit no `error.alert` line). On a quiet site the
  count floor dominates; see the
  [aggregate alarm section](runbook-alerts.md#aggregate-spike-alarm-errorspike).
- `queue.failing` covers terminal queue failures. Retryable failures do not page
  until terminal; inspect the retry-cause records for context.
- The scheduled Tail Worker probe checks `/up` every minute (two attempts per
  run) and alerts only after health has stayed red for over two minutes. Runs
  landing on a five-minute boundary also run the synthetic main-flow checks
  (`/`, `/events`, `/join`, `/login`), alerting after two failed attempts in one run
  per check (see the
  [alert runbook](runbook-alerts.md#synthetic-main-flow-checks-syntheticdown)).
  Together they detect sustained unavailability, a broken conversion page,
  and a broken sign-in entry redirect, not the Discord authorize hop or a
  full Discord OAuth round trip: the sign-in check stops at `/login`
  because the next hop mints OAuth state and probing it would write
  production auth rows, and the conversion check stops at the `/join`
  page for the same reason (the `/join/discord` hop mints journey state).
- Discord notifications are allowlisted, redacted summaries. Trace-derived
  summaries carry the exact source `script`, a fixed logs dashboard path, and
  the deployed `build_sha` when the trace carries one (version tag, else
  its release-tagged log lines; live traces do not populate the tag); no
  summary ever contains a request ID, exception text, or URL. Correlate them
  with source logs as before.
- Cloudflare Workers Observability is the configured error/logging surface; this
  repository does not configure a Sentry SDK. The production GitHub Release
  identifies the promoted commit, and structured request/error/queue log lines
  are tagged with that same commit as `build_sha` and `release`. Staging and
  production `/up` expose their deploy version metadata.
- Production rollout uses the shared 5/50/100 gradual promotion action with
  per-stage health/SLO gates and automatic rollback on a failed gate. Each
  stage also judges a live error-rate signal: after a soak, the gate queries
  Cloudflare GraphQL Analytics (`workersInvocationsAdaptive`, filtered to the
  promoted `scriptVersion`) over the window since that stage's smoke gate
  finished — so the smoke probes themselves never count toward the sample or
  the rate — and fails the stage — into the same automatic rollback — when
  the new version's invocation error rate exceeds the configured threshold
  (defaults: rate 0.05, at least 20 post-smoke invocations, window capped at
  a 10-minute lookback). Invocation errors are unhandled exceptions,
  exceeded resources and internal errors; a handled HTTP 500 response does not
  count, so this complements rather than replaces the smoke gate. Below the
  minimum sample the gate retries while analytics aggregates catch up, then
  passes with a warning; a failing analytics query fails the stage closed.
  Prove changes to this gate with the manual `error-rate-gate-rehearsal`
  workflow (live staging signal plus a simulated elevated rate), never
  against production. See [production promotion and rollback](runbook.md).

These limitations are explicit: do not treat a healthy `/up`, an absent Discord
page, or a GitHub Release as proof that the full user journey is healthy. The
error-rate gate watches only promotion stages, not steady-state traffic, and
the aggregate alarm covers error volume and crashes, not journey correctness.
Expand detection only through a reviewed change with staging evidence and
passive production verification.

## Safe verification

Use the authenticated alert probe and require both fresh redacted Tail receipts
on staging, as described in
[the alert delivery drill](runbook-alerts.md#probe-parity-request-error--self-failing-queued-job).
The probe deliberately returns HTTP 500 and may emit one synthetic terminal queue
failure; it must not be run against production. For log correlation and redaction
tests, see [request-log tests](../test/request-log.test.ts) and
[alert redaction tests](../test/tail-alerts.test.ts).

Never put webhook URLs, tokens, cookies, OAuth callback parameters, member IDs,
raw traces, or raw Tail streams in an issue, PR, or shared incident note. Use
only the redacted probe result and the deployed 40-hex source SHA as evidence.
