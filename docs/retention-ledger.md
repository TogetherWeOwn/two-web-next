# Member-data retention ledger (L7 first slice)

First slice of the whole-schema retention ledger ([post-cutover-milestone.md](post-cutover-milestone.md#carried-items), L7): one row per member-data table with its retention window, prune mechanism, and proof. All decisions below already landed — this ledger publishes and pins them, changing no policy.

Pinned by `../test/retention-ledger.test.ts`. Do not change a window or mechanism here without changing the code and the test together.

Age-only delete (`occurred_at < cutoff AND occurred_at < clock_timestamp() - interval '2160 hours'`); cutoff-exact rows survive. The append-only trigger (`drizzle/1018`) refuses deletes younger than 90 days by the database clock. Idempotent re-run matches nothing. | [What is retained and why](member-erasure.md#what-is-retained-and-why), `src/jobs/cron.ts`, `src/jobs/constants.ts` |

| `web_throttle_hits` | 5-minute rolling (`THROTTLE_COUNTER_RETENTION_MINUTES = 5`) | RSVP path prunes counters older than five minutes before judging the budget (`pruneThrottle` in `src/events/rsvp.ts:321-325`): at most one 1,000-row batch per write (`order by id limit 1000 for update skip locked` over `where at < clock_timestamp() - make_interval(mins => ...)`), so rows locked by unrelated transactions are skipped for a later pass and fresh rows are never targets. The join admission path (`checkJoinThrottle` in `src/join/service.ts`) judges and records first, then prunes expired rows after every verdict, admitted or refused: at most one 1,000-row oldest-first batch per request (`order by id limit 1000 for update skip locked` over `where at < now() - make_interval(mins => ...)`), outside the admission lock and best-effort so a throw keeps the decided verdict. Five minutes is an age cutoff, not a deletion timer. Cleanup is lazy and path-dependent: expired rows can linger on a quiet site until a later request that runs cleanup; for example, an unknown-event RSVP id exits before the shared prune. | [Throttle buckets](member-erasure.md#throttle-buckets-ephemeral-self-deleting), `src/events/rsvp.ts:321-325`, `src/join/service.ts` |

The TTL bounds how long a session stays readable; the sweep bounds how long after expiry the row lingers. Expiry-exact rows go; live rows stay; caller-ahead skew rows are skipped, never over-deleted. Each statement deletes at most 1,000 rows (`PRUNE_DELETE_BATCH_SIZE = 1000`), up to 100 batches per pass (`PRUNE_DELETE_MAX_BATCHES = 100`). | `queue_jobs` | Message lifetime normally (dispatch until the consumer settles the row); orphaned rows retained indefinitely until a reviewed operator correction (no age window) | No age prune by design (`pgQueueLedger` in `src/jobs/postgres.ts`: "No sweep" — an age test cannot tell a transport-paused backlog from an orphan, so deleting by age undercounts live depth). Lifecycle transitions only: `enqueued` → `reserved`/`released` → `dequeued` on success, `failed` on terminal failure (which moves the row into `queue_failed_jobs` and retires the live row). Settlement is best-effort: a failed compensation stays visible as backlog (`src/jobs/ledger.ts`), a failed or timed-out ledger write still acknowledges the message, and malformed carriers are acknowledged without any ledger transition (`consume` in `src/jobs/consumer.ts`); those orphan rows stay until a reviewed operator correction ([Queue containment, drain and failed-job replay](runbook.md#queue-containment-drain-and-failed-job-replay)). `/up` reports, never deletes. | `src/jobs/postgres.ts`, `src/jobs/consumer.ts`, `src/jobs/types.ts` |
| `queue_failed_jobs` | Retain indefinitely until operator-confirmed discard (no age window) | Terminal failures land one row per dispatch `jobId` (`failed`, fenced so the first failure wins; a redelivery retires the live row without inflating failed depth). Removal is exactly one row by id via `discardFailedJob` — library-only, no operational route deletes a row. Guarded re-dispatch never touches the dead row; only a later confirmed recovery discards it. Listing (`listFailedJobs`) is read-only. | [Queue dead-letter redrive runbook](queue-redrive-runbook.md), `src/jobs/redrive.ts`, `src/jobs/postgres.ts` |
| `job_unique_locks` | 300-second lease validity (`SYNC_EVENT.uniqueForSeconds = 300`, the Laravel `$uniqueFor` port) plus daily expiry sweep | Daily `model:prune` via `pruneModelTables` → `drainPruneTable` → `pgPruneStores().jobUniqueLocks.sweepExpired(now)`: deletes only leases expired by both clocks (`expires_at <= now` AND `expires_at <= clock_timestamp()`, mirroring the session sweep). The TTL bounds how long a lease stays valid; the sweep bounds how long after expiry the row lingers. Expiry-exact rows go; live leases stay; caller-ahead skew rows are skipped, never over-deleted. Each statement deletes at most 1,000 rows (`PRUNE_DELETE_BATCH_SIZE = 1000`), up to 100 batches per pass (`PRUNE_DELETE_MAX_BATCHES = 100`). A full final batch emits a cap warning with `jobUniqueLocks` in `cappedTables`; older rows drain on a later pass. Idempotent. Acquire still wins only over expired rows (`pgUniqueLock.acquire`); release still compare-deletes by owner token, so an expired carrier cannot release a successor's lease. The worker runs this sweep on its autocommit dispatch pool, outside the single-flight prune transaction: the sweep deletes the exact rows acquire targets, so holding its row locks until the whole pass commits would block concurrent acquires — each batch commits (and releases its row locks) when its own statement finishes, while the flight's advisory lock still gives mutual exclusion. The outer DELETE rechecks `expires_at <= now` alongside the candidate keys, so a lease renewed by a concurrent acquire between candidate selection and deletion survives. | `src/jobs/constants.ts`, `src/jobs/cron.ts`, `src/jobs/postgres.ts`, `src/jobs/worker.ts`, `src/jobs/sync-event.ts`, `src/jobs/consumer.ts` |

## Scope

- Queue, lock, and sync-attempt rows (`queue_jobs`, `queue_failed_jobs`, `job_unique_locks`, `event_sync_attempts`) are published above.
- Agent-event rows (`agent_events` retired, `agent_event_grants`, `agent_event_hits`, `agent_event_audits`, `agent_event_idempotency_keys`) are published above.
- Core member tables (`users`, `profiles`, `rsvps`, `events`, `featured_contents`, `discord_event_snapshots`, `web_oauth_journeys`) are published above.
- No policy or CISO decision changes in this slice; no retention window or prune behavior changes.
