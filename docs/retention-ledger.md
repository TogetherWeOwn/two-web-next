# Member-data retention ledger (L7 first slice)

First slice of the whole-schema retention ledger ([post-cutover-milestone.md](post-cutover-milestone.md#carried-items), L7): one row per member-data table with its retention window, prune mechanism, and proof. All decisions below already landed — this ledger publishes and pins them, changing no policy.

Pinned by `../test/retention-ledger.test.ts`. Do not change a window or mechanism here without changing the code and the test together.

| Table | Retention window | Prune mechanism | Proof |
|---|---|---|---|
| `member_data_access_logs` | 90 days (`MEMBER_ACCESS_LOG_RETENTION_DAYS = 90`) | Daily `model:prune` via `pruneModelTables`: `accessLog.pruneOlderThan(cutoff(now, 90 days))`. Age-only delete (`occurred_at < cutoff AND occurred_at < clock_timestamp() - interval '2160 hours'`); cutoff-exact rows survive. The append-only trigger (`drizzle/1018`) refuses deletes younger than 90 days by the database clock. Idempotent re-run matches nothing. | [What is retained and why](member-erasure.md#what-is-retained-and-why), `src/jobs/cron.ts`, `src/jobs/constants.ts` |
| `activity_log` | Retain indefinitely per CISO decision | No job prunes it. The table is append-only; although the database trigger permits deletion after 90 days, nothing does so — that exception stays an unused safety valve. Revisit only through the whole-schema retention ledger. | [What is retained and why](member-erasure.md#what-is-retained-and-why) |
| `web_throttle_hits` | 5-minute rolling (`THROTTLE_COUNTER_RETENTION_MINUTES = 5`) | RSVP path prunes counters older than five minutes before judging the budget (`pruneThrottle` in `src/events/rsvp.ts:282-286`): at most one 1,000-row batch per write (`order by id limit 1000 for update skip locked` over `where at < clock_timestamp() - make_interval(mins => ...)`), so rows locked by unrelated transactions are skipped for a later pass and fresh rows are never targets. The join admission path (`checkJoinThrottle` in `src/join/service.ts`) judges and records first, then prunes expired rows after every verdict, admitted or refused: at most one 1,000-row oldest-first batch per request (`order by id limit 1000 for update skip locked` over `where at < now() - make_interval(mins => ...)`), outside the admission lock and best-effort so a throw keeps the decided verdict. Five minutes is an age cutoff, not a deletion timer. Cleanup is lazy and path-dependent: expired rows can linger on a quiet site until a later request that runs cleanup; for example, an unknown-event RSVP id exits before the shared prune. | [Throttle buckets](member-erasure.md#throttle-buckets-ephemeral-self-deleting), `src/events/rsvp.ts:282-286`, `src/join/service.ts` |
| `web_sessions` | 2-hour TTL (`SESSION_TTL_SECONDS = 7200`) plus daily expiry sweep | Daily `model:prune` via `pruneModelTables` → `drainPruneTable` → scheduled session adapter `sweepExpired(now)`: deletes only rows expired by both clocks (`expires_at <= now` AND `expires_at <= clock_timestamp()`). The TTL bounds how long a session stays readable; the sweep bounds how long after expiry the row lingers. Expiry-exact rows go; live rows stay; caller-ahead skew rows are skipped, never over-deleted. Each statement deletes at most 1,000 rows (`PRUNE_DELETE_BATCH_SIZE = 1000`), up to 100 batches per pass (`PRUNE_DELETE_MAX_BATCHES = 100`). A full final batch pages once via `scheduled.failing@model:prune` (one redacted line, no table detail) and still returns its counts; older rows drain on a later pass. Idempotent. | `src/jobs/cron.ts`, `src/jobs/constants.ts`, `src/jobs/postgres.ts`, `src/sessions.ts` |
| `join_attempts` | 90 days (`JOIN_ATTEMPT_RETENTION_DAYS = 90`) | Daily `model:prune` via `pruneModelTables`: `joinAttempts.pruneOlderThan(cutoff(now, 90 days))`. Age-only delete (`created_at < cutoff`); cutoff-exact rows survive. Idempotent re-run matches nothing. | `src/jobs/cron.ts`, `src/jobs/constants.ts` |
| `queue_jobs` | Message lifetime normally (dispatch until the consumer settles the row); orphaned rows retained indefinitely until a reviewed operator correction (no age window) | No age prune by design (`pgQueueLedger` in `src/jobs/postgres.ts`: "No sweep" — an age test cannot tell a transport-paused backlog from an orphan, so deleting by age undercounts live depth). Lifecycle transitions only: `enqueued` → `reserved`/`released` → `dequeued` on success, `failed` on terminal failure (which moves the row into `queue_failed_jobs` and retires the live row). Settlement is best-effort: a failed compensation stays visible as backlog (`src/jobs/ledger.ts`), a failed or timed-out ledger write still acknowledges the message, and malformed carriers are acknowledged without any ledger transition (`consume` in `src/jobs/consumer.ts`); those orphan rows stay until a reviewed operator correction ([Queue containment, drain and failed-job replay](runbook.md#queue-containment-drain-and-failed-job-replay)). `/up` reports, never deletes. | `src/jobs/postgres.ts`, `src/jobs/consumer.ts`, `src/jobs/types.ts` |
| `queue_failed_jobs` | Retain indefinitely until operator-confirmed discard (no age window) | Terminal failures land one row per dispatch `jobId` (`failed`, fenced so the first failure wins; a redelivery retires the live row without inflating failed depth). Removal is exactly one row by id via `discardFailedJob` — library-only, no operational route deletes a row. Guarded re-dispatch never touches the dead row; only a later confirmed recovery discards it. Listing (`listFailedJobs`) is read-only. | [Queue dead-letter redrive runbook](queue-redrive-runbook.md), `src/jobs/redrive.ts`, `src/jobs/postgres.ts` |
| `job_unique_locks` | 300-second lease validity (`SYNC_EVENT.uniqueForSeconds = 300`, the Laravel `$uniqueFor` port) plus daily expiry sweep | Daily `model:prune` via `pruneModelTables` → `drainPruneTable` → `pgPruneStores().jobUniqueLocks.sweepExpired(now)`: deletes only leases expired by both clocks (`expires_at <= now` AND `expires_at <= clock_timestamp()`, mirroring the session sweep). The TTL bounds how long a lease stays valid; the sweep bounds how long after expiry the row lingers. Expiry-exact rows go; live leases stay; caller-ahead skew rows are skipped, never over-deleted. Each statement deletes at most 1,000 rows (`PRUNE_DELETE_BATCH_SIZE = 1000`), up to 100 batches per pass (`PRUNE_DELETE_MAX_BATCHES = 100`). A full final batch emits a cap warning with `jobUniqueLocks` in `cappedTables`; older rows drain on a later pass. Idempotent. Acquire still wins only over expired rows (`pgUniqueLock.acquire`); release still compare-deletes by owner token, so an expired carrier cannot release a successor's lease. The worker runs this sweep on its autocommit dispatch pool, outside the single-flight prune transaction: the sweep deletes the exact rows acquire targets, so holding its row locks until the whole pass commits would block concurrent acquires — each batch commits (and releases its row locks) when its own statement finishes, while the flight's advisory lock still gives mutual exclusion. The outer DELETE rechecks `expires_at <= now` alongside the candidate keys, so a lease renewed by a concurrent acquire between candidate selection and deletion survives. | `src/jobs/constants.ts`, `src/jobs/cron.ts`, `src/jobs/postgres.ts`, `src/jobs/worker.ts`, `src/jobs/sync-event.ts`, `src/jobs/consumer.ts` |
| `event_sync_attempts` (`public`, Drizzle `eventSyncAttempts`) | No age window in code: settled snapshots are retained indefinitely so late redelivery cannot replay edits. The only removal is the `ON DELETE cascade` foreign key when the parent `events` row is deleted; no app path deletes events. | Sole writer is `pgEventStore` in `src/jobs/events.ts`: `prepareSync` inserts one immutable snapshot row per idempotency key (one pending row per event via `event_sync_attempts_pending_idx`); `claimSync` retires stale never-attempted snapshots to `obsolete` or fences a due request (`request_attempts + 1`, `next_attempt_at = null`); `deferSync` reschedules `next_attempt_at`; `completeSync` settles to `succeeded` and acknowledges the revision; `failSync` settles definitive refusals to `failed`. Readers are the recovery and eligibility checks (`needsSync`, `staleEventKeys`, `pendingSync`, `hasFailedSync`) plus the admin source-evidence verifier (`stale_keys`, `failed_sync`, `pending_sync`). No prune store exists: `PruneStores` and `pruneModelTables` cover six age-pruned tables plus the session and lock sweeps, and no retention-days constant names sync attempts. `delete from event_sync_attempts` appears only in test fixtures as cleanup. | [Migration](../drizzle/1020_event-sync-revisions.sql), [schema](../src/db/admin-schema.ts), [store](../src/jobs/events.ts), [prune wiring](../src/jobs/cron.ts), [prune stores](../src/jobs/postgres.ts), [admin reads](../src/admin/source-evidence.ts), [queue containment, drain and failed-job replay](runbook.md#queue-containment-drain-and-failed-job-replay) |
| `event_search_logs` (`public`, Drizzle `eventSearchLogs`) | 90-day cutoff (`EVENT_SEARCH_LOG_RETENTION_DAYS = 90`); rows strictly older than the daily cutoff are eligible. The prune pass deletes in batches of 1,000, up to 100 batches per table per pass; if the cap is reached, older rows may remain pending until a later pass. | The daily `model:prune` cron calls `pruneModelTables`, which drains batches using `occurred_at < cutoff`; cutoff-exact and newer rows survive. Runtime writer: `recordSearch` logs normalized query and result count for first-page event searches; import writer: `bin/import/content-funnel.mjs` imports retained legacy rows. Readers: `topZeroResultSearches` feeds the admin dashboard's optional zero-result widget; `src/db/read-classification.ts` restricts its aggregate query. | `drizzle/1005_event-search-logs.sql`, `src/db/admin-schema.ts`, `src/events/page-models.server.ts`, `src/events/search-log.ts`, `src/admin/routes.tsx`, `src/db/read-classification.ts`, `src/jobs/constants.ts`, `src/jobs/cron.ts`, `src/jobs/postgres.ts`, `test/prune.test.ts`, `test/event-search.test.ts`, `bin/import/content-funnel.mjs` |
| `board_view_logs` (`public`, Drizzle `boardViewLogs`) | 90-day eligibility, not a deletion deadline (`BOARD_VIEW_LOG_RETENTION_DAYS = 90`). | Anonymous usage fields: `id`, `normalized_board_key`, `scope`, `season`, `result_count`, `occurred_at`; no user ID, session, Discord ID, IP, or username. Hono (`src/hotzones/routes.tsx`, `src/leaderboards/routes.tsx`) and Kit (`src/kit-hotzones.ts`, `web/src/hooks.server.ts`) use best-effort `recordBoardView`; anonymous describes the record, not necessarily the visitor.
